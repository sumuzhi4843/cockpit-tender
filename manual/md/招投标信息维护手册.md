## 前言

### 本手册写给谁

招投标驾驶舱（cockpit :5310）的后台数据维护人员。手册回答三类问题：

1. **数据从哪来**：22 个网站各怎么抓、存到哪（第一~四章 + 第一部分）
2. **数据怎么归类**：区县怎么判、ICT/行业/类型怎么分（第二、三部分）
3. **系统怎么维护**：定时任务、质量门禁、补抓、监控、备份、踩坑（第四章 + 第四部分）

### 名词术语

| 术语 | 含义 |
|---|---|
| **公告类型** | 单条公告是什么：招标 / 中标 / 意向 / 其他（`notice_type`） |
| **项目状态** | 一个项目进行到哪：待开标 / 已中标 / 待跟踪……（`project_stage`） |
| **S1–S4** | 抓取方式分级：静态 HTML / API 直连 / CDP 浏览器 / PDF 提取 |
| **0 级区县** | 平台自带权威区县码（苏服采 areaCode、江苏政采 zone_code、本地站硬编码），最高优先级 |
| **L0.5 外地过滤** | 招标人以外市行政区开头（武汉市/台州市/纳雍县…）→ 全国站外地项目，不参与盐城区县判定 |
| **富化** | 从公告正文提取结构化字段（发包人/金额/开标时间/中标单位）并打标签 |
| **ICT** | 信息化/智能化相关项目（强词 1 个或弱词 2 个命中） |
| **账本** | 苏服采分页抓取对账表（每桶抓了多少 vs 接口总量），用于校验不漏抓 |
| **质量门禁** | verify_quality.py 只读校验，不通过则部署保留线上旧数据 |
| **Schema v2/v3** | 项目级视图 `projects[]` 为主列表；v3（2026-09-29）= SQLite→8002 API 唯一出口，tender.json 下线 |

## 总览：一个公告的旅程

```
各站公告 → ①抓取（scrapers.py / ccgp_scraper.py）→ 入库去重（store_db.py）
→ ②分类（enrich_engine / analyzer）→ ③富化打标（enrich_engine / enrich_meta）
→ ④项目归并+生命周期（project_engine）→ 质量门禁（verify_quality）
→ 质量门禁 → SQLite 发布（deploy.sh；前端经 8002 API 即时读取，无静态 JSON）
```

| 主线 | 回答的问题 | 关键文件 |
|---|---|---|
| **抓取** | 从哪拿、拿到多少条 | `scrapers.py` + `ccgp_scraper.py` + `run.py` + `config.py` |
| **分类** | 这是什么公告（类型/子类型/ICT/行业） | `enrich_engine.py` + `analyzer.py` + `notice_classifier.py` |
| **富化标签** | 谁发包、多少钱、何时开标、中标单位、区县/中小微 | `enrich_engine.py` + `enrich_meta.py` |
| **项目归并** | 多站公告归并成项目、推进到哪个阶段 | `project_engine.py` + `build_project_links.py` |
| **辅助** | 存储去重、质量门禁、补抓、监控、备份 | `store_db.py` / `verify_quality.py` / 各 `backfill_*` |

### 示例：射阳县盘湾中学高压增容工程

| 时间 | 事件 | 项目状态 |
|---|---|---|
| 08-11 | 3 站（盐城政采/江苏政采/中国政采）发布采购公告 | upcoming（开标日 08-24 在未来） |
| 08-13 | 3 站发布更正公告 | 不变 |
| 08-24 15:00 | **开标时间已过**，尚无成交公告 | **pending_result（待跟踪）** |
| 08-25 | 3 站发布成交公告（中标：江苏海益电气工程有限公司） | awarded（历史中标） |

> 关键认知：**"待跟踪结果"不是故障**。它是项目开标日已过、但系统尚未抓到候选/成交结果时的中间态；抓到成交公告后自动转"历史中标"（详见项目状态章节）。

### 两个易混淆点

- **公告类型 ≠ 项目状态**：`award` 是公告类型（这条公告是"中标"），`awarded` 是项目状态（这个项目"已中标"）。
- 分类/富化是对**已入库**公告的加工，中间隔着存储与去重（见第四部分）。

## 抓取规则

### S1–S4 分级

| 级别 | 方式 | 适用站点 |
|---|---|---|
| **S1** | requests + BeautifulSoup 静态解析 | 本地 5 站、悦达、三峡、农华、国投、一汽、政采类等 12 站 |
| **S2** | JSON/POST API 直连 | 中粮、奇瑞、江苏招标平台、盐城交易网、苏服采 |
| **S3** | CDP 无头浏览器渲染（headless Chromium + 验证码 OCR 回退） | 江苏政府采购网（单站超时 4500s） |
| **S4** | PDF 正文提取（下载 PDF 提文本层 / OCR） | 中国邮政（补抓）、江苏招标平台中标+**招标公告**（2026-09-20 起全子类型：列表页只存 69 字摘要，正文在详情 PDF） |

> 分级实现见 `scrapers.py` 中 `get_all_scrapers()` 的类绑定；每站细节见**第一部分逐站档案**。

### 分桶抓取（权威来源）

| 站 | 参数 | 覆盖 |
|---|---|---|
| 苏服采 | `area_codes` 12 码（320900 + 9 区县 + 320991 经开 + 320992 盐南） | 全市分桶；**每条 row 自带 areaCode** |
| 江苏政采 | `target_zones` 11 码（TARGET_ZONES） | 亭湖/盐都/大丰/响水/滨海/阜宁/射阳/建湖/东台/经开/盐南 |

> 两站都按区县码逐桶查询、每条公告 100% 自带区县码 → 归类直接用（0 级，禁止二次猜测）。

### 抓取边界

- **目标范围**：盐城市域（含 9 区县 + 盐南/经开两功能区）；中国政府采购网按关键词"盐城"搜索。
- **一汽电子采购**：`scope=盐城市`，只抓盐城分公司项目，整站划入盐开区。
- **非盐城源**（三峡集团等）不设区县，作为"全市"背景数据。
- **瑞康医院**：2026-08-25 退役（`RETIRED_SITES`），不再抓取/补抓/展示；历史 DB 保留 10 条。

### 去重与幂等

| 机制 | 位置 | 作用 |
|---|---|---|
| `notices` UPSERT（md5 id） | store_db.py | 公告只增不减，重复抓取自动覆盖，永不删除 |
| `store.json` MD5 | 报告推送 | 仅控制报告推送去重，**不影响** API 数据输出（DB 恒全量） |
| 苏服采 `source_key = source_id\|project_key` | sufucai_ledger.py | 原始项目索引幂等，防同 id 不同 project 撞库 |
| `projects / project_notices / project_links` | project_engine.py | 每次采集**重建**（非累积） |

### 部署链路（deploy.sh 状态机）

```
collect → backfill（含 M1 失败站即时重试）→ rebuild → verify → publish（含 .gz 预压缩）→ audit → screen → completed
```

- `logs/run_state.json` deployment 段：当前阶段（覆盖 run.py 退出后的补抓/发布期）
- `logs/run_state.json` manifest 段：SQLite 发布清单（schema v3：quick_check + notices/projects/ict 行数 + 发布时间）
- **发布保护**：质量门禁通过 + JSON/DB 数量一致 + 本轮生成时间，才 `docker cp`；任一失败保留线上旧数据
- **M1 失败站即时重试（2026-09-07）**：backfill 段开头读 `run_state.json` failures 段，非空则 `timeout 2700 deep_refresher.py --sites <失败站>` 立即重试（写库后随本轮发布）；仍失败留给凌晨 deep-a/b 双兕底
- **日志轮转（2026-09-07 H2）**：cron.log 超 20MB 自动归档 gzip（保留 7 份）；工具 `scripts/rotate_log.sh`

### 单站超时、并发与心跳

- **并发采集（2026-09-07 H1）**：快站 21 个走线程池（`CRAWL_CONCURRENCY=4`，环境变量可调），慢站（江苏政采）主线程串行与快站**同时**跑；总时长 = max(两组)。每 scraper 独立 session 无线程安全问题；状态文件写入加锁 + `_atomic_json` 线程安全（tmp 名含线程 id）。
- 单站超时默认 1800s；江苏政采 4500s + SIGALRM 强制兕底（2026-09-07 补，站内 deadline 自检失效时也能截断），超时只告警**不杀全局**，交给即时重试/凌晨补偿。
- **江苏政采增量水位（2026-09-07 N1）**：公告按日期倒序，整页早于 30 天（`CCGP_RECENT_DAYS` 环境变量，设 0 禁用）即停翻页——根治每轮重翻全量历史（实测旧逻辑 75min 只新增 2 条），预期 10-15min 完成。
- 进程心跳 `run_state.json` heartbeat 段每 60s 写一次；健康快照 `health_snapshot.py` 每 5 分钟落一份；**主抓超 3h 报 crawl_overrun high 告警（2026-09-07 L6）**。
- 并发下 `run_state.crawl` 的 current_site 字段为最后写入值（多线程覆盖），仅作提示不参与告警判定。

### 2.3 ICT 分类（analyzer.py）

**判定规则（2026-09-06 方案 B 三层，词表在 config.py）**

- **硬否决**（ICT_NON_ICT_WORDS）：标题命中招租/出租/食堂/保洁/物业/CA证书/电子签章/装修等 → 直接非 ICT。**否决词只查标题、严禁扫正文**（正文含扶贫/模板条款，扫正文曾误杀 80 条真 ICT）
- **强匹配**（34 词，1 个即判定，不受否决影响）：视频监控、监控系统、弱电、安防、智能化、网络设备、交换机、路由器、防火墙、综合布线、门禁、停车场系统、LED大屏、数据中心、算力、动环监控、物联网、IoT、视频会议、会议系统、光纤、5G、UPS、精密空调、数字孪生、BIM、数据底座、数据空间、智能化工程、安防工程、弱电工程、智慧城市、智慧交通、智慧社区
- **弱匹配**（17 词，需 ≥2 个 + 业务动作词）：大数据、平台、AI、人工智能、机房、智慧、软件、信息系统、服务器、存储、通信、传感器、电子政务、云计算、广播、数字化、信息化；若另命中弱否决（立项咨询/咨询服务/检测服务/快检等）则此档不判（有强词仍判）
- 匹配范围：强词看标题 + 正文前 2000 字；弱词意向/招标公告看标题 + 正文前 2000 字，其他类型仅看标题
- 产出：公告级 `notices.ict_keywords`（JSON 数组）；项目级 `projects.is_ict` 物化列（关联公告命中词并集）由 project_engine 重建时写入

- 展示：标题前红色 `● ICT` 角标 + 行左侧红边；**悬停角标显示命中词**（「ICT 命中：安防、平台、监控系统」）；移动端点开卡片详情有「关键词」行（强词红/弱词蓝）

### 2.5 项目分类三层

**① 公告类型（notice_type / notice_subtype）**——enrich_engine.classify_notice

| 一级类型 | 子类型 | 判定 |
|---|---|---|
| `tender` | tender_notice / tender_reopen | 招标/采购公告（含二次/重新采购） |
| `award` | award_final / award_candidate | 中标结果/成交公告；中标候选人公示 |
| `intention` | intention | 采购意向/招标计划/预算公告 |
| `other` | correction/failed/terminated/suspended/contract/unknown | 更正/流废标/终止/暂停/合同/未识别 |

- 正文兜底：标题未命中时从正文识别（「中标单位：」「本项目终止采购」等明确标志词，前 500 字限制防误判）

**② 项目状态（project_engine.py `_stage`，12 种）**

| 状态 | 判定 |
|---|---|
| terminated | 存在终止公告 |
| awarded | 存在最终中标/成交公告；或中标候选人公示（尚无最终结果） |
| failed | 本轮流标/废标且未发现重新采购 |

### 3.5 经验样本库（experience_samples.json）

**为什么需要**：scraper 会遇到「页面数据在，但默认抽取器漏抽」的边缘 case（例：城南新区中标公示页有 6+ 种 label 变体「中标价（元）」「中标价（ 元 ）」「中标价格 (元)」，默认 extractor 只认标准形式）。如果不沉淀经验，下次碰到同类问题又要重新调研。本节把这类「页面有数据 + 怎么抽到」沉淀成可复用样本。

**当前阶段**：L2 半自动（BaseScraper.scrape() 末尾已钩装 `experience_auto.install()`，扫每条 item 匹配经验库，空字段自动 fetch + 抽字段 + 写回 item；老板仍负责报告新 case + 写新经验）。L3 全自动（仅 LLM 置信度 >0.95 才入库）暂不考虑。

**L1 → L2 → L3 升级路径**：
- L1：手工跑 `experience_apply.py --run` 验证（老板报告 → 我手工入经验 → 手工跑工具）
- **L2（当前）：钩子嵌入 scraper 末，主流程后自动套用**（老板报告 → 我写经验 → 以后同场景 scraper 自动补齐）
- L3（未来）：LLM 在线分析「哪些字段又漏了」自动入库新经验（待 L2 跑满 30+ 条样本后再议）

#### 3.5.4 统一入口 apply_unified（v3，2026-10-02）

**架构入口**：`experience_auto.apply_unified(notice_id, mode='db_first|db_or_fetch|full')`

**3-tier 级联**（按成本从低到高）：

- **Tier 1：DB content 直抽**（10ms/条）——读 `raw_json.content`，跑经验库 extractor
- **Tier 2：refetch URL**（500ms + 风控 delay）——`fetcher.fetch()` + extractor（仅 `db_or_fetch`/`full` 触发）
- **Tier 3：Playwright 渲染**（5-10s/条，仅 JS 站 + `full` 触发）——`playwright_fetch()` + extractor

**4 类触发时机**（运行时机保留独立）：

| 触发 | 入口 | mode |
|---|---|---|
| L2 hook（BaseScraper.scrape 末） | `install()` 钩子里调 | `db_first` ⚠️禁止 `full` |
| cron 凌晨补 | `site_refresher.sh deep-a/b` 末段调 `_unified_apply.py` | `db_or_fetch` |
| deploy.sh M1 重试 | 末段补 1 行调 | 同上 |
| 一性回灌 | 手动 `_unified_apply.py --site=xxx` | `db_or_fetch`/`full` |
| legacy 调用（deprecation） | `apply_pending_to_db` / `apply_from_db_content` 薄壳 | 内部 `_unified_loop()` |

**L2 hook 安全守则**：⚠️ hot path（`patched_scrape`）**必须** `mode='db_first'`。若改成 `full`，每条 item 会触发 Playwright，主抓速度爆降 50-100 倍。`test_apply_unified.py::test_6` 静态检查保证这一点。

**为什么合并**：老机制（`backfill_*.py` 11 个 + `site_refresher.sh`）+ 新机制（`apply_pending_to_db` / `apply_from_db_content`）Goal 同 / Output 同 / Input 同（项目信息空字段），但触发时机 + 数据源不同。合并为单函数 `apply_unified` + `_unified_loop` 批量 helper，老脚本改薄壳调用。**新站零成本**（写一条经验记录即可）。

**Phase 1.5 兼容性矩阵**（2 周 deprecation 周期）：

| 老函数 | 新实现 |
|---|---|
| `apply_pending_to_db(db_path, max_n, sites_filter, dry_run)` | `_unified_loop(mode='db_or_fetch')` |
| `apply_from_db_content(db_path, max_n, sites_filter)` | `_unified_loop(mode='db_first')` |
| 11 个 `backfill_*.py` 一次性脚本 | `_unified_apply.py --site=X --max=N` |

- `run_state` heartbeat 段 2 分钟内更新 + PID 存活 = 正常运行

- 单站超时：默认 1800s，江苏政采 4500s（只告警，不杀进程）
- 同一站连续两轮 failed = 站点级高危，交凌晨补偿或人工

├────────────────────────────────────────────────────────────────┤
